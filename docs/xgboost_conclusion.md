## 4. Error analysis 

- **ปีที่พลาดมากที่สุด:** 2019 (MAE 0.313) และ 2022–2023 (0.305) — ปีที่ระดับโรคเปลี่ยนแรง (2022–23 คลื่นใหญ่) ส่วน 2024–2025 ง่ายกว่า (0.271 / 0.259)
- **Bias:** โมเดล **ทำนายต่ำเกินจริงในปีที่คลื่นแรง** (2022 mean D = +0.099 แต่ pred = −0.010; 2023 D = +0.088, pred = −0.042) → regression to the mean ของ regression บน target ที่มี distribution เปลี่ยน
- **ทิศทาง:** แถว "ชะลอลง (D<−0.05)" ที่มีผู้ป่วยน้อยพลาดหนักที่สุด (MAE 0.455) — ค่า D ติดลบแรงจากฐานต่ำ
- **เขต:** เขต 1 (กทม./ปริมณฑล), 4, 3 ยากที่สุด (MAE ≈ 0.31–0.33) ; เขต 13 ง่ายที่สุด (0.198)
- **Calibration:** สหสัมพันธ์ pred กับ D รายปี = 0.61–0.74 (ทิศทางถูก) แต่ค่าเฉลี่ยเบี้ย

## 5. ผล data drift / online ML (โปรโตคอลหน้าต่าง 2/4/6/12 เดือน)

**โปรโตคอล:** origin = 1 ม.ค. ของปี 2019, 2022–2025 (หลัก) + 2020–2021 (เสริม) · train = label ที่รู้แล้วในหน้าต่าง (cutoff − W เดือน, cutoff] · test = **ทุกแถวหลัง origin จนจบข้อมูล (31 ธ.ค. 2025)** แบ่งบล็อก 4 สัปดาห์ · R² ต่อบล็อก (guard n≥30, std(y)>0) · จุด drift = บล็อกแรกที่ **R² < 0** · climatology ของอากาศ fit จากข้อมูลก่อน origin เท่านั้น
ผลรวม: **2,474 บล็อก, ~1,853 ครั้งของการ fit, ใช้เวลา 1,924 วินาที** → `drift_r2_by_block.csv`, `drift_summary.csv`

### 5.3 ข้อสรุปสำหรับนำเสนอ (5 ข้อ)

1. **ตอบโจทย์ตรง ๆ: R² เริ่มตกที่ ~11 สัปดาห์ (≈2.5 เดือน)** สำหรับโมเดลที่ถูกล็อกด้วยหน้าต่าง 2–12 เดือน — ตกเร็วและตกแรง (บางปีถึง −2.9) ทุกขนาดหน้าต่าง ทุกปี origin
2. **หน้าต่างสั้น = ยาพิษ ไม่ใช่ยาอายุวัฒนะ:** static 2 เดือนแย่ที่สุด (MAE 0.451, R² −1.14); ยิ่งหน้าต่างยาวยิ่งดีขึ้น แต่ **ไม่มีหน้าต่างไหนชนะ "ไม่ใช้หน้าต่างเลย" (full history)** — ข้อมูลเก่าไม่ใช่พิษ แต่คือบริบทที่โมเดลต้องใช้ (ระดับพื้นฐาน/ฤดูของแต่ละจังหวัด)
3. **Online ML ทุก 4 สัปดาห์ ไม่คุ้มถ้าใช้หน้าต่างสั้น:** refit ลด MAE เพียง 3.5% (0.407 → 0.393) และ R² ยังติดลบทั้งหมด — ถ้าต้องออนไลน์ ให้ **refit แบบ expanding (full history)** ทุก 4 สัปดาห์ หรืออย่างต่ำหน้าต่าง 12 เดือน (refit12 ดีกว่า static12 ถึง 13%)
4. **"data drift" ที่เห็นจริงคือจุดเปลี่ยนระดับคลื่น ไม่ใช่การเสื่อมสภาพช้า ๆ:** ปี **2023** ทำให้ทุกแบบติดลบตั้งแต่บล็อกแรก (0–4 สัปดาห์) ส่วน full history ที่ origin 2024/2025 **อยู่รอดจนจบข้อมูล** (R² +0.24 ตลอด) — จึงไม่ใช่กรณี "โมเดลเก่า ๆ เน่าตามเวลา"
5. **R² ต่อบล็อกมี variance สูงมาก** (ต่ำสุด −12.1, ค่ามัธยฐาน −0.22) — ต้องดูค่าเฉลี่ย/มัธยฐานข้าม origin หรือตามช่วงเดือน (ดูกราฟ `drift_r2_mean_horizon.png`) ห้ามสรุปจากบล็อกเดียว

## 6. ความเข้าใจเชิงลึกของโมเดลตัวเอง (XGBoost)

### 6.1 โมเดลทำงานอย่างไร (ใช้ตอบข้อ 1)

**XGBoost = Gradient Boosting บนต้นไม้ตัดสินใจ** เริ่มจากค่าคงที่ (ในเคสนี้ค่ามัธยฐานของ D เพราะใช้ loss = absolute error)
แล้วเพิ่มต้นไม้ทีละต้น ต้นไม้ตัวที่ `n` ถูกสร้างจาก **ค่าผิดพลาด (gradient) ของต้นก่อน ๆ** → ต้นไม้แต่ละต้นแก้จุดที่ยังเหลืออยู่

| พารามิเตอร์ที่ใช้ (ค่าที่ tune ได้) | ค่า | เหตุผล |
|---|---|---|
| `objective` | `reg:absoluteerror` | Loss = ค่าผิดพลาดสัมบูรณ์ สอดคล้องกับ metric หลัก **MAE** และทนค่าผิดปกติ (mitigate outlier) |
| `n_estimators` × `learning_rate` | 500 × 0.03 (tune แล้ว) | ต้นไม้เยอะ + เรียนรู้ช้า = ค่อย ๆ ไล่เก็บ error ไม่ memorize |
| `max_depth` | 4 | จำกัดความลึก กันต้นไม้จดจำจังหวัด/ช่วงเวลาเป็น block |
| `min_child_weight` | 10 (tune แล้ว) | ใบต้องมีมวล residue พอ → ไม่แตกเป็นใบเล็ก ๆ ที่ฟิต noise |
| `subsample` / `colsample_bytree` | 0.8 / 0.8 | สุ่มแถวและคอลัมน์ต่อต้น = regularization เชิงสุ่ม (bagging + feature bagging) |
| `reg_lambda` (L2) | 5.0 | ปรับน้ำหนักใบให้เล็ก |
| `random_state` | 342 | ทำซ้ำได้เหมือนเดิมทุกครั้ง |

จุดแข็งที่ใช้ในงานนี้: **ไม่ต้อง scale ฟีเจอร์, จับ interaction ที่ไม่เป็นเส้นตรงได้เอง** (เช่น ฝน × ฤดู × เขตสุขภาพ)
และ hyperparameter **บอบบางมาก** — tune ทั้งกริด 12 ค่า ได้ MAE 0.3041 → โมเดลสุดท้าย 0.2893 (ส่วนใหญ่มาจากฟีเจอร์ ไม่ใช่ parameter)

### 6.2 ฟีเจอร์ไหนสำคัญจริง (permutation importance, dMAE เฉลี่ย 5 fold)

| กลุ่ม     | จำนวนฟีเจอร์ | dMAE เฉลี่ย | อ่านว่าอย่างไร                                                                        |
| --------- | ------------ | ----------- | ------------------------------------------------------------------------------------- |
| `hist_`   | 7            | **+0.0543** | ประวัติใกล้เคียงของจังหวัดคือสัญญาณหลัก                                               |
| **`my_`** | **35**       | **+0.0429** | **ฟีเจอร์ที่ออกแบบจากสมมติฐาน = กลุ่มสำคัญอันดับ 2** (เกือบเท่า hist_ ที่มีแค่ 7 ตัว) |
| `seas_`   | 4            | +0.0348     | ฤดู (ฮาร์โมนิก) ยังจำเป็น                                                             |
| `nat_`    | 3            | +0.0187     | ระดับประเทศช่วยเสริม                                                                  |
| `wx_`     | 15           | +0.0083     | อากาศดิบ lag 0–4 **แทบไม่มีค่าเมื่อมี `my_` แล้ว**                                    |
| `reg_`    | 13           | +0.0019     | dummy เขต ไม่มีผล (โมเดลใช้ `hist_` รายจังหวัดแทน)                                    |

**อ่านเข้าข้างตัว:** ฝน/อากาศ "ย้ายเข้าไปอยู่ใน `my_`" หมด (`my_rain_cum4`, `lag5–8`, `spike`, `z52`, `rain_x_season`)
เพราะถูกจัดวางตาม **lag ทางชีววิทยา 4–8 สัปดาห์** ซึ่งให้ค่ามากกว่าการใส่ lag ดิบ ๆ ตามปฏิทิน
→ สมมติฐานที่ออกแบบมา **แทนที่** ข้อมูลดิบได้จริง (ดูได้จาก F3 anomaly ที่ไม่ช่วยเลย)

### 6.3 บทเรียนเชิงเปรียบเทียบกับโมเดลอื่น (ใช้ตอบข้อ 3)

1. **โมเดลไม่ใช่ตัวแปรหลัก ฟีเจอร์ต่างหากคือตัวแปรหลัก:** ที่ชุดฟีเจอร์ F1 เดียวกัน XGBoost (0.3019) กลับ**แพ้** HGB (0.2977) และ Ridge (0.2991) เล็กน้อย — ชัยชนะของงานนี้มาจาก `my_*` + อากาศดิบ (0.3019 → 0.2907 = −3.7%) มากกว่าความซับซ้อนของโมเดล
2. **ทุกโมเดลมีจุดแข็งคนละแบบ:** Ridge/HGB เสถียรกว่าบนฟีเจอร์พื้นฐาน, XGBoost ทำคะแนนได้ดีที่สุดเมื่อได้ฟีเจอร์ที่มี interaction ให้จับ (F2/F6), เทมเพลตสอนว่า "baseline ต้องมาก่อน" ซึ่งยืนยันว่า skill 0.276 นั้นมาจากข้อมูลไม่ใช่เทคนิค
3. **ข้อจำกัดที่ต้องยอมรับ (regression to the mean):** โมเดล **ทำนายต่ำเกินจริงในปีคลื่นแรง** — 2022 mean D = +0.099 แต่ pred = −0.010, 2023 D = +0.088 / pred = −0.042 (corr รายปี 0.61–0.74 = **ทิศทางถูก แต่ amplitude แบน**) → ถ้าต้องการจับ "คลื่นใหญ่" ควรเพิ่มตัวแปรระดับฤดู (เช่น cumulative epidemic pressure) หรือโมเดลสองขั้น (ทำนายขนาดคลื่นก่อน แล้วค่อยทำนายทิศทาง)
4. **ฟีเจอร์ anomaly (`wxa_`) มีต้นทุนสูงแต่ไม่ได้ผล:** CI คร่อม 0 (−0.94 ถึง +1.53) เพราะ target D **เป็นค่าความเปลี่ยนแปลงอยู่แล้ว** → anomaly ซ้ำซ้อนกับการ normalize ของ target และต้อง fit จาก train (เสี่ยง leakage) — เสนอให้ทีมตัดออก
5. **บทเรียนจากโปรโตคอล drift (ข้อ 5):** โมเดลตัวนี้ **ต้องการ history ยาว** — การฝึกด้วยหน้าต่าง 2–12 เดือนทำให้ R² ติดลบใน 11 สัปดาห์ ดังนั้นถ้า deploy จริง ควรใช้ **full history + refit ทุก 4 สัปดาห์** ไม่ใช่ sliding window สั้น ๆ
